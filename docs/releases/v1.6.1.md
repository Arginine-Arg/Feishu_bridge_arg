# arg-bridge v1.6.1

修复第三方 API 配置下 Codex 因 `OPENAI_API_KEY` 为空而无法启动的问题，并补齐 tmux structured 连接的文档。

## 第三方 provider 凭据

- Bridge 拉起的 Codex 不再受 shell 启动文件影响。`cc-switch` 等工具写入的 `export OPENAI_API_KEY="${token:-$OPENAI_API_KEY}"` 会让变量以空字符串存在，而 Codex 对声明了 `env_key = "OPENAI_API_KEY"` 的第三方 provider 会直接报 `Missing environment variable: OPENAI_API_KEY`，即使配置里已有 `experimental_bearer_token` 也不会兜底。
- 每次 Codex 运行前，Bridge 读取 `$CODEX_HOME/config.toml` 的 `model_provider` 与 `[model_providers.<id>]`，判断该 provider 是否为第三方（`base_url` 不在 `api.openai.com` / `chatgpt.com`，或使用自定义 provider id），再按以下顺序补齐它声明的 `env_key`（默认 `OPENAI_API_KEY`）：
  - 环境里已存在的非空值始终优先，不覆盖显式导出的 key；
  - 其次使用 `experimental_bearer_token`；
  - 最后回退到 `auth.json`。
- **官方路径不受影响**：`model_provider = "openai"` 或 `preferred_auth_method = "chatgpt"` 时不注入任何变量，官方 API key 与 ChatGPT OAuth 登录行为与之前完全一致。
- 确认是第三方 provider 但找不到任何 token 时，只记录 `codex-credential-missing` 日志并继续启动，不阻塞 preflight。

## tmux 环境传递

- live pane 之前只固定代理变量，`CODEX_HOME` 和 provider 凭据不会进入 pane。现在通过显式 `env KEY=VALUE` 前缀传递，因此 `respawn-pane`（tmux 没有 `-e` 参数）和 Ctrl-C 之后重建的 pane 同样生效。
- 相同注入覆盖 turn 模式的 `codex exec`、live tmux pane、legacy pane 迁移后的 structured App Server 与替换 TUI，以及 `arg-bridge native`。

## 验证

- 真实复现：在本机 config.toml（`model_provider = "deepseek"`、`env_key = "OPENAI_API_KEY"`、`experimental_bearer_token`）下用空 `OPENAI_API_KEY` 运行，Codex CLI 0.155.1 报 `Missing environment variable: OPENAI_API_KEY`；补入 token 后继续正常发起请求。
- 端到端回归：用假 Codex 二进制在空 `OPENAI_API_KEY` 下运行 adapter，子进程实际收到 config 中的 token。
- 新增单元测试覆盖配置解析（含注释、profile 覆盖、带引号 provider 名）、官方 / OAuth 不注入、`auth.json` 回退、自定义 `env_key`、已有 key 优先；真实 tmux 端到端测试确认凭据进入 pane 进程。
