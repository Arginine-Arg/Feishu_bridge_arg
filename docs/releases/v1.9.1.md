# arg-bridge v1.9.1

This release adds mid-turn Feishu steering and an explicit Bridge-managed
native TUI path.

## Mid-turn steering

Normal messages sent while a Codex task is running no longer have to wait for
the entire turn to finish:

- the structured backend calls `turn/steer` with the exact active turn ID;
- a live Codex terminal writes the message into the empty composer and uses the
  native Tab-to-queue shortcut;
- steering calls are serialized per chat scope and do not start another
  Bridge run;
- a known rejection falls back to the normal post-turn queue;
- an uncertain timeout is reported and never replayed automatically;
- `/stop`, `/goal`, `/btw`, picker controls, side conversations, attachments
  and quoted batches keep their existing routing.

The native Codex turn remains authoritative; Bridge does not interrupt or
restart it merely to deliver a follow-up.

## New commands

```bash
arg-bridge native --bridge
arg-bridge native --adopt <old-thread-id>
```

`--bridge` starts a new Bridge-managed Codex thread with `arg_bridge.*`
dynamic tools. The Bridge process keeps the tool host alive while the native TUI
is attached, so delegation goes through MixAgents Broker using ordinary
plaintext tasks.

`--yolo` and `--dangerously-bypass-approvals-and-sandbox` now share one
permission resolver for new Codex sessions. `--sandbox` and
`--ask-for-approval` are validated by the same path. Resume consumes those
flags but inherits the thread's frozen permissions and never sends overrides to
`thread/resume`.

`--adopt` safely migrates an old session:

- requires an idle old thread;
- reads only user/assistant text;
- redacts common secret patterns;
- caps the handoff at 12,000 characters;
- starts a new dynamic-tool thread;
- injects the bounded handoff;
- prints both old and new thread IDs.

Codex 0.164 exposes `dynamicTools` on `thread/start` but not
`thread/resume`, so an old thread cannot be made dynamic by editing JSONL,
adding a marker, or silently pretending the same thread ID was upgraded.

Ordinary `arg-bridge native` remains ordinary Codex except that it now resolves
the actual writer owner before reconnecting. Existing Bridge-marked threads can
be attached with:

```bash
arg-bridge native --bridge <thread-id>
```

## Validation

The release includes an actual Codex App Server process test for:

- `turn/steer` with an exact active turn while a dynamic tool call is blocked,
  followed by the steered text in the next provider request;
- live-terminal Tab-to-queue steering and Feishu fallback/uncertain handling;
- new Bridge thread dynamic tools;
- a real `arg_bridge.spawn_agent`/`wait_agent` round trip;
- reattaching a persisted Bridge thread;
- cold-resuming that thread after its owning test App Server exits;
- legacy-thread text migration and `thread/inject_items`;
- marker `adoptedFrom` evidence;
- bounded history redaction and truncation.

The release also retains the v1.8.1 real cc-switch/MixAgents three-round
worker test, native dynamic-tool protocol tests, full unit/integration/process
suites, build and package installation checks.

## Resume fixes

- A thread with a live writer now reconnects to that exact App Server. A host
  that can merely read the same persisted history is no longer misidentified as
  the owner.
- Live-owner and cold reattachment preserve the provider/model stored in the
  thread instead of applying a newly selected cc-switch route. A missing
  historical provider is reported rather than silently replaced.
- Closing the TUI only unsubscribes the Bridge-side writer and closes its RPC
  channel. It does not stop the App Server or interrupt a running turn.
- The reconnect command printed by Codex uses the resolved backend socket. A
  temporary router socket may disappear after exit without invalidating that
  command.
- Unknown writer ownership fails closed with the PID; Bridge never deletes lock
  files, force-kills an owner or starts a competing writer.
- The first spontaneous TUI disconnect remains a separate, unproven issue; no
  root cause is claimed for it in this release.
