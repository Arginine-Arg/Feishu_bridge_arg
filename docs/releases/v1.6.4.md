# arg-bridge v1.6.4

修复 bridge 托管的 tmux session 丢失"文件发送能力"的问题：换 pane、重启 Codex、或 Ctrl-C 之后，`arg-bridge sendfile` 现在仍然可用。

## 问题

桥接发送能力由 `ArtifactBroker` 按 scope 签发的持久令牌提供，agent 通过 `ARG_BRIDGE_ARTIFACT_SOCKET` / `ARG_BRIDGE_ARTIFACT_TOKEN` 找到它。此前这两个变量只注入到 bridge **直接拉起**的那个进程环境里：

- 托管 session 的 tmux 环境里没有它们；
- 共享 App Server daemon（`codex app-server --listen`）也不会继承；
- 因此一旦用户在 pane 里重启 Codex、Ctrl-C 后重建 pane、或通过共享 daemon 启动工具，agent 就再也找不到 broker，`arg-bridge sendfile` 报“当前进程没有 bridge 文件发送能力”。

实测复现：崩溃前进程有没有这两个变量，直接决定了发送是否可用（bridge 直接拉起的 app-server 有，外部重启后拉起的 daemon 没有）。

## 修复

1. **写入 tmux session 环境**：bridge 启动 live/structured 托管会话时，把本次运行的 scoped 凭据通过 helper 写入该 session 的 tmux 环境（`set-environment`），并在新建 session 时用 `-e` 一并注入。这样后续任何在此 session 内新建或重建的 pane 都会继承，包括用户在 pane 内手动 `codex --resume` 的场景。
2. **结构化会话同步刷新**：`StructuredView.ensureNative(artifactEnv)` 现在在每轮运行后把最新凭据刷新到该 view session 的环境里，`/tmux bind` 到结构化 pane 的 scope 同样受益。
3. 外部绑定的 tmux session 依旧**不写入**这些变量（一个外部 session 可能属于多个 scope，写进去会造成串号）。

## 验证

- 新增真实 tmux 测试：bridge 拉起 agent 时带上 scoped 凭据，agent 进程能读到，并且该 session 的 `tmux show-environment` 里存在两个变量（pane 重建后仍可发送）。
- 手工复现：修复前 agent 进程读到空值，修复后读到 `ARG_BRIDGE_ARTIFACT_TOKEN=scope-token-123`，与 broker 记录一致。
- 全量 `pnpm test`：131 个文件 / 1012 passed、0 failed。

## 边界说明

历史数据库（`thread_history_1.sqlite`）损坏、以及共享磁盘上的 `file is not a database` 属于存储层问题，不在本次修复范围内；bridge 侧能做的是保证凭据传递不再丢失。
